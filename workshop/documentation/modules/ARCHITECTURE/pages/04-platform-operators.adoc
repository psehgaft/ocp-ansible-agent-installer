= Platform Operator Lifecycle and Day-2 Services

Module 4.4 establishes a repeatable lifecycle for platform operators and their operands. The workflow separates operator installation from service configuration, supports direct and GitOps delivery, and requires explicit readiness evidence before dependent services are installed.

== Learning objectives

After completing this module, you can:

* Select supported packages and channels for the target OpenShift release.
* Install catalog-backed operators with reusable lifecycle automation.
* Render reviewed manifests for GitOps reconciliation.
* Configure operands only after their CRDs and controllers are ready.
* Protect registry, storage, cloud, PKI, and backup credentials.
* Validate Subscriptions, InstallPlans, CSVs, ClusterOperators, workloads, routes, storage, and custom-resource conditions.
* Record rollback boundaries and evidence for every platform capability.

== Execution model

Use the individual playbooks for focused exercises or the orchestrator for a complete environment:

[source,bash]
----
ansible-playbook playbooks/day2/platform-operators.yml \
  -e @inventories/lab/group_vars/all/platform-operators.yml

ansible-playbook playbooks/day2/platform-logging.yml \
  -e platform_deployment_mode=gitops
----

The shared `platform-operator-bundle.yml` validates input, invokes the catalog lifecycle roles, applies operand resources in direct mode, and renders resources in render or GitOps mode. Do not place passwords, private keys, pull secrets, object-storage credentials, or cloud credentials in unencrypted inventory.

== Recommended dependency order

. cert-manager and PKI trust.
. Storage and network foundations.
. Monitoring, logging, observability, and backup.
. ACM and ACS.
. Virtualization and MTV.
. AAP and Quay.
. Bare-metal, load-balancer, and RHOSO services.

[#acm]
== 4.4.1 Advanced Cluster Management

Install ACM with `playbooks/day2/acm.yml`. Configure `MultiClusterHub`, observability, governance, policies, placements, and managed-cluster integration through `acm_resources`. Validate the Subscription and CSV in `open-cluster-management`, `MultiClusterHub` conditions, hub workloads, and managed-cluster availability.

[#acs]
== 4.4.2 Advanced Cluster Security

Install ACS with `playbooks/day2/acs.yml`. Supply `Central`, `SecuredCluster`, scanner, admission-control, and integration resources through `acs_resources`. Store central credentials and external integrations in Vault or an external secret manager. Validate Central, scanner, collector, admission control, and secured-cluster connectivity.

[#storage]
== 4.4.3 Storage Platform Services

Select storage according to workload access modes, failure domains, performance, snapshots, encryption, expansion, and recovery requirements. Never claim raw devices that contain data or belong to another storage stack.

[#lvm-storage]
=== 4.4.3.1 LVM Storage Operator

Use `playbooks/day2/platform-lvm-storage.yml` with an explicit `lvm_storage_resources` list containing the Namespace, OperatorGroup, Subscription, and `LVMCluster` resources appropriate to the target catalog. Validate device classes, thin-pool sizing, node selection, StorageClasses, expansion, and VolumeSnapshotClass behavior.

[#local-storage]
=== 4.4.3.2 Local Storage Operator

Use `playbooks/day2/platform-local-storage.yml` with `local_storage_resources`. Configure LocalVolume or LocalVolumeSet resources only after confirming stable device paths and node affinity. Validate PV creation, StorageClass binding mode, reclaim policy, and recovery procedures.

[#odf]
=== 4.4.3.3 OpenShift Data Foundation

Use `playbooks/day2/storage.yml`. Define `storage_operator_resources` for `StorageSystem`, `StorageCluster`, external-mode resources, and supporting secrets. Validate topology, raw-device ownership, capacity, Ceph health, object storage, StorageClasses, snapshots, and failure-domain resilience.

[#csi-drivers]
=== 4.4.3.4 Enterprise CSI Drivers

Use `playbooks/day2/platform-csi-drivers.yml` with reviewed `csi_driver_resources` for Pure Storage, HPE, NetApp, or another supported vendor. Include vendor operator or Helm resources, credentials from protected inputs, StorageClasses, VolumeSnapshotClasses, and topology configuration. Confirm the support matrix and image sources before deployment.

[#virtualization]
== 4.4.4 OpenShift Virtualization

Use `playbooks/day2/virtualization.yml`. Define the `HyperConverged` custom resource and optional migration network, storage profiles, templates, and policies in `virtualization_resources`. Validate CPU virtualization extensions, node placement, DataVolume imports, VM startup, and live migration.

[#mtv]
== 4.4.5 Migration Toolkit for Virtualization

Use `playbooks/day2/mtv.yml` only after OpenShift Virtualization is healthy. Store source-platform credentials securely and define ForkliftController, Providers, NetworkMaps, StorageMaps, and Plans in `mtv_resources`. Test discovery and a noncritical migration before production waves.

[#aap]
== 4.4.6 Ansible Automation Platform

Use `playbooks/day2/aap.yml` with an explicit `aap_resources` list. Include Namespace, OperatorGroup, Subscription, and required AAP custom resources. Validate the selected channel against the catalog, configure persistent storage and routes, and protect controller, hub, database, and external-service credentials.

[#cert-manager]
== 4.4.7 cert-manager Operator

Run `platform-cert-manager.yml` to install the operator, then the existing `cert-manager.yml` operand workflow for Issuers, ClusterIssuers, and Certificates. Validate controller readiness, issuer conditions, certificate SANs, renewal, and resulting Secrets.

[#pki]
== 4.4.8 Platform PKI and Trust

Use `platform-pki.yml` with `pki_resources` for trust bundles, API and Ingress certificates, Proxy trusted CA configuration, and certificate policies. Validate chain order, SANs, key usage, client trust, expiry, and rollback before replacing serving certificates.

[#quay]
== 4.4.9 Quay and Registry Services

Use `platform-quay.yml`. Define QuayRegistry, object storage, database, route, TLS, Clair, mirroring, and registry-policy resources in `quay_resources`. Protect robot tokens and storage/database credentials and verify push, pull, scanning, mirroring, and retention.

[#networking]
== 4.4.10 Network Foundation Operators

Use `platform-networking.yml` for NMState, SR-IOV, and MetalLB lifecycle. Define NodeNetworkConfigurationPolicy, NetworkAttachmentDefinition, SriovNetworkNodePolicy, SriovNetwork, IPAddressPool, advertisements, and peer resources in `networking_operator_resources`. Validate IOMMU, firmware, NIC ownership, VLANs, MTU, address overlap, and rollback connectivity.

[#monitoring]
== 4.4.11 Platform Monitoring

Use `platform-monitoring.yml` with a nonempty `monitoring_resources` list for cluster-monitoring configuration, user-workload monitoring, ServiceMonitor, PodMonitor, PrometheusRule, AlertmanagerConfig, storage, retention, and scheduling. Validate targets, rules, alerts, PVC usage, and remote-write destinations.

[#logging]
== 4.4.12 Cluster Logging and Loki

Use `platform-logging.yml` to install Loki before Cluster Logging. Provide LokiStack, ClusterLogForwarder, storage, TLS, output, pipeline, and tenancy resources in `logging_resources`. Validate collector flow, object storage, retention, forwarding destinations, and backpressure.

[#oadp]
== 4.4.13 Backup and Restore with OADP

Use `platform-oadp.yml` with an explicit `oadp_operator_resources` list, then run the existing `oadp.yml` operand workflow. Include Namespace, OperatorGroup, Subscription, DataProtectionApplication, BackupStorageLocation, VolumeSnapshotLocation, and protected credential references. Prove recovery with test Backup and Restore objects.

[#cluster-observability]
== 4.4.14 Cluster Observability Operator

Use `platform-cluster-observability.yml`. Define MonitoringStack, UIPlugin, ServiceMonitor, PrometheusRule, storage, and tenancy resources through `cluster_observability_resources`. Ensure the design complements rather than duplicates built-in monitoring.

[#network-observability]
== 4.4.15 Network Observability Operator

Use `platform-network-observability.yml` with an explicit `network_observability_resources` list that includes lifecycle resources and FlowCollector configuration. Size eBPF sampling, Loki or Kafka, storage, retention, and console integration according to traffic volume.

[#baremetal]
== 4.4.16 Bare Metal Operator

Use `platform-baremetal.yml` for cluster-payload configuration and BareMetalHost resources. Validate BMC connectivity, credentials, boot MACs, inspection, provisioning network mode, and host operational status before automated provisioning.

[#load-balancer]
== 4.4.17 MetalLB Load Balancing

Use `platform-load-balancer.yml`. Define MetalLB, IPAddressPool, L2Advertisement, BGPAdvertisement, BGPPeer, and BFDProfile resources in `load_balancer_resources`. Reserve nonoverlapping addresses and test failover and upstream routing.

[#rhoso]
== 4.4.18 Red Hat OpenStack Services on OpenShift

Use `platform-rhoso.yml` after cert-manager and NMState are healthy. Define OpenStackControlPlane, data-plane node sets and deployments, network isolation, secrets, and storage integration in `rhoso_resources`. Validate all operator CSVs, control-plane conditions, data-plane Ansible execution, endpoints, and network reachability.

== Common validation and evidence

[source,bash]
----
oc get subscriptions.operators.coreos.com -A
oc get installplans.operators.coreos.com -A
oc get csv -A
oc get co
oc get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
oc get events -A --sort-by=.lastTimestamp | tail -100
----

For each service, capture the selected package and channel, approval decision, Namespace, Subscription, InstallPlan, CSV, controller workloads, custom-resource conditions, routes, PVC usage, warnings, rollback instructions, and validation timestamp.
